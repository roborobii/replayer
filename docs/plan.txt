# Xen Rebirth — Reverse Engineering Plan

## Goal
Build a private offline server for Secret of the Solstice / Xen Online by reverse engineering the client and protocol used against the live Xen Rebirth server. Stay undetected during observation; end state is a self-hosted emulator that survives Xen Rebirth shutting down.

## Architecture

```
┌─ Windows host ──────────────────────────────────────────────┐
│                                                             │
│  ┌──── Guest VM (Windows) ────┐                             │
│  │   game client (only)       │ ──► vNIC ──► vSwitch ──► [Internet]
│  └────────────────────────────┘                  │          │
│         ▲                                        │          │
│         │ .vmem (guest physical RAM)             │          │
│         │                                        │          │
│  ┌──────┴────────────────────────────────────────┴───────┐  │
│  │  HOST-SIDE PARSING & ANALYSIS                         │  │
│  │  ─────────────────────────────────────                │  │
│  │  Memory: MemProcFS → guest PID for game client        │  │
│  │          → AOB scans, pointer chains, struct walks    │  │
│  │  Network: pktmon/Wireshark on vSwitch                 │  │
│  │           filter = host <xen_ip> and port <game_port> │  │
│  │  Static: Ghidra on copied client files                │  │
│  │  Decoder: Python (Scapy/struct) over filtered pcaps   │  │
│  │  Emulator: built & tested on host; client redirected  │  │
│  │            via guest hosts file                       │  │
│  └───────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────┘
```

**Guest** = VM running only the game client.
**Host** = physical machine running everything else.
**Scope** = memory pinned to game PID, network pinned to Xen Rebirth IP+port.

## Detection model

| Vector | Visible to guest? |
|---|---|
| Host reads `.vmem` | No |
| Host captures vSwitch | No |
| Static analysis on copied files | No |
| Behavioral anomalies (impossible movement, replays) | Yes — don't do them |
| **VM presence (CPUID, SMBIOS, MAC, services)** | **Yes — only real risk** |

Mitigation: Since the client logs in and plays, it doesn't seem to be detected

| Job | Tool |
|---|---|
| Hypervisor | VMware Workstation Pro (free; flat `.vmem` file) |
| Guest memory introspection | MemProcFS + PCILeech |
| Network capture | pktmon (built-in) or Wireshark on VMnet adapter |
| Static analysis | Ghidra |
| Protocol decoder | Python + Scapy |
| Emulator reference | rAthena source (closest architectural cousin) |

## Phases

### 0. Setup (1 day)
- Install VMware Workstation Pro on host.
- Create Windows guest VM. Snapshot before installing client.
- Install game client in guest. Snapshot after install.
- Verify client connects and plays normally.
- Copy entire client install dir from guest to host for static work.

### 1. Static analysis (host, offline) — no detection risk
- Run **Detect It Easy** on the EXE; unpack if packed.
- Load in Ghidra. Find:
  - `recv` / `WSAStartup` → packet dispatch table
  - Crypto constants → cipher + key derivation
  - File format parsers → asset structures
  - Anticheat strings → confirm absence
- Save Ghidra project; reference throughout later phases.

### 2. Network capture (host vSwitch) — undetectable
- Identify Xen Rebirth IP+port (one wide capture or `strings` on EXE).
- Filter capture to that endpoint only:
  ```
  pktmon filter add game -i <xen_ip> -p <game_port>
  pktmon start --capture --pkt-size 0 -f C:\cap\session.etl
  pktmon stop
  pktmon etl2pcap C:\cap\session.etl -o C:\cap\session.pcapng
  ```
- Build Wireshark Lua dissector for the opcode field.
- Pair packets with in-game actions (walk, chat, attack); build opcode dictionary.
- Cross-reference dispatch table from Phase 1.
- Decode encryption using cipher + key derivation found in Phase 1.

### 3. Memory analysis (host MemProcFS) — undetectable
- Mount guest memory:
  ```
  MemProcFS.exe -device "C:\VMs\GameClient\GameClient.vmem" -mount M:
  ```
- Scope to game PID only: `M:\name\<pid>-<client>.exe\vmem`.
- Find player object, entity table, world state via AOB scans + pointer chains.
- Reconcile with structures from Phase 1.

### 4. Emulator development (host, offline)
- Build minimal TCP server in Go/Rust/Python that speaks the decoded protocol.
- Redirect client by editing guest `hosts` file:
  ```
  <host_lan_ip>  <xenrebirth_hostname>
  ```
- Iterate: login → char select → world entry → walk → chat → combat.
- Free use of debuggers / breakpoints now (local server, no risk).

### 5. Content reconstruction
- Parse client data files (item DB, skill DB, map data) using formats from Phase 1.
- Slurp community wikis (Xen Online Fandom, etc.) for stats, drops, quest data.
- Behavioral observation for what isn't documented.

## Scoping discipline

- **Memory**: never enumerate all guest processes. Open by name, read by virtual address.
- **Network**: filter at capture time on `host <xen_ip> and port <game_port>`. No wide captures past Phase 2 discovery.
- **Files**: copy game dir once; refresh only on client patches.

## Daily workflow

1. Start guest VM (snapshotted clean state).
2. Launch client; play with intent (e.g., "today I capture skill packets").
3. Capture filtered pcap on host.
4. Read targeted memory ranges via MemProcFS.
5. Stop VM.
6. Analyze on host. Update Ghidra notes, decoder, emulator.
7. Snapshot revert if anything drifted.

## Verification milestones

- [ ] Default VM logs into Xen Rebirth without issues
- [ ] First decoded packet (login response)
- [ ] Opcode dictionary covers ≥80% of common gameplay packets
- [ ] Emulator accepts client login → reaches character select
- [ ] Emulator drives client into world; player can walk
- [ ] Emulator handles combat, inventory, chat
- [ ] Content DB seeded; offline play viable
