  recording_<id>_mem.delta.zst.
  3. Replay: start from baseline, walk the delta log forward applying changed pages. You can reconstruct memory at any
  timestamp.

  - Static stuff (~60–80%): zero deltas. Free.

  second.

  changed only when an interesting event fired."

  The page-delta scan is 95% of the cost. To keep it invisible:

  1. Read vmemd\*.vvmem files, not memory.vmem with seeks. MemProcFS caches vmemd contents aggressively; sequential
  reads of cached regions don't pause the guest. Random seeks into memory.vmem do. Your existing scan_vmt_instances
  already uses vmemd — keep doing that.
  2. Adaptive scanning (the big win): after baseline, classify each page by churn:
    - Stable for ≥10 ticks → demote to "cold" tier, scan every 10th tick
    - Changed in last tick → "hot" tier, scan every tick
    - Most of a 400 MB heap is cold (loaded textures, item DB, code-shaped data, string pools). After 30s of warm-up,
  you're typically scanning <50 MB/tick instead of 400 MB. 5–10× reduction.
  3. Skip image-backed regions entirely. vvmem regions whose name contains .dll / .exe are already filtered.
  Texture/asset regions show up as anonymous heap but are stable — adaptive scanning catches them in tier 2.
  4. Hash + diff on a worker thread, not the read thread. Read thread streams pages out of vmemd as fast as MemProcFS
  can serve them; hash/diff/compress happens on a separate thread with a bounded queue. Decouples disk-write
  back-pressure from read cadence.
  5. Bound CPU at 1 core. zstd-multithread off (single thread, level 3 not 19). Compression is the easiest place to
  accidentally peg CPU and it gives you nothing — zstd-3 is already 3 GB/s and within ~10% of zstd-19's ratio on random
  binary data.

  Realistic total impact at 1 Hz with adaptive scanning, after warm-up: host CPU ~5–15% of one core, guest
  ~unmeasurable. Hyper-V live introspection is the same mechanism EDR products use; a game client can't time-check
  against it without an external trusted clock, and they don't.

  Lever you can tune at runtime: -MemHz 1 (default), -MemHz 0.5 if you ever see a hint of stutter, -MemHz 2 if you want
  finer resolution and the guest's not reacting.

  Filesystem capture — you're right to be skeptical

  Skip it. Reasons:

  1. MemProcFS doesn't give you guest filesystem cleanly. It only reconstructs files currently in the page cache
  (M:\forensic\), which is partial and unpredictable.
  2. Doing it properly means VSS-snapshotting the VHDX from the host. Stealth-safe but operationally heavy and overlaps
  almost completely with what the memory baseline already captures (game writes things to disk, but those things first
  existed in process memory).
  3. You don't need it for replay. Replay drives the live client which will recreate its own logs/caches.
  4. For RE, memory deltas dominate. Anything the client cares about is in RAM at some point.

  If a specific file ever turns out to matter (e.g. a chat log only the game writes), we can add an opportunistic VSS
  snapshot at session-end as a one-line PowerShell cmdlet (Checkpoint-VM or New-VMSnapshot against the VHDX). Doesn't
  need to be in the hot path. Punt until you have a concrete use case.

  What can be deferred vs what can't                                                                                    
  M:\ is a live view of guest RAM, not a time machine. Reading it at t+5 gives you the memory state at t+5, not the       state at t. So we can't queue a "snapshot point" and read it later — by then the bytes have changed and the timestamp
  would be a lie.

  What that means in practice:

  ┌─────────────────────────────────────────┬──────────────────────────────────────────┐
  │             Pipeline stage              │           Can it be deferred?            │
  ├─────────────────────────────────────────┼──────────────────────────────────────────┤
  │ The read itself (open(vvmem).read())    │ No — must happen at snapshot time        │
  ├─────────────────────────────────────────┼──────────────────────────────────────────┤
  │ Hashing pages                           │ Yes                                      │
  ├─────────────────────────────────────────┼──────────────────────────────────────────┤
  │ Diffing against last hashes             │ Yes                                      │
  ├─────────────────────────────────────────┼──────────────────────────────────────────┤
  │ Compressing changed pages               │ Yes                                      │
  ├─────────────────────────────────────────┼──────────────────────────────────────────┤
  │ Writing to disk                         │ Yes                                      │
  ├─────────────────────────────────────────┼──────────────────────────────────────────┤
  │ Updating the JSONL with mem_delta event │ Yes (with timestamp from capture moment) │
  └─────────────────────────────────────────┴──────────────────────────────────────────┘

  So: read on time, process on a worker. That's what I was proposing already, and I should have explained it more
  clearly.

  The "right order" guarantee — easier than you'd think

  You don't actually need clever queuing for ordering. You just need a single global atomic seq counter:

  JsonlWriter.next_seq()  # under one mutex, monotonic

  Every event — net frame, form change, memory delta chunk, sync — calls next_seq() at the moment of capture, not at the
   moment of write. The number is allocated synchronously; the write can happen whenever. Replay sorts by seq and is
  guaranteed correctly ordered regardless of how late the writer thread got around to flushing it.

  Pcap is its own file with its own per-packet timestamps from the same hardware clock — already correctly ordered
  internally. Cross-correlating pcap to JSONL is by timestamp comparison post-hoc; they can't be assigned the same seq
  because tshark doesn't know about it. That's fine.

  The actual deferred-processing architecture

  [Read thread] (must run on cadence)
      ├─ open vmemd files, read pages
      ├─ stamp t_mono_ns, allocate seq for this snapshot
      └─ push (seq, t, raw_pages) onto bounded queue → return immediately

  [Worker thread] (drains queue at its own pace)
      ├─ hash pages, diff vs last
      ├─ zstd-compress changed pages
      ├─ append to .mem.delta.zst
      └─ emit JSONL event with original (seq, t)

  If the worker falls behind, the bounded queue back-pressures the reader. You get one of:
  - A skipped tick, logged as {"kind":"mem_skip","reason":"queue_full","seq":...} so you know about it
  - A throttled cadence

  Either is preferable to letting the queue grow unboundedly into RAM. The reader never blocks the rest of the system,
  and ordering is preserved because seq is allocated at capture time, not write time.

  What this enables

  - Memory thread can take all the time it wants compressing without slowing the form-poller or the network sniffer
  - Disk I/O hiccups (e.g. antivirus stalling a write) won't propagate back to MemProcFS reads
  - We can cheaply add zstd-19 long-mode (better ratio, slow) on the worker because the read thread doesn't care
  - A burst of activity (lots of changed pages all at once) gets smoothed out

  Bottom line

  - Reads themselves are real-time, but cheap and on a single dedicated thread. ~50–150 MB/s of cached vmemd reads is
  well within MemProcFS's capability without taxing the guest.
  - Everything downstream is async with a bounded queue. No back-pressure to the reader except via explicit skip events.
  - Ordering is via a global seq counter assigned at capture time, not by timestamp comparison or write order.
